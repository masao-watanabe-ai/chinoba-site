Research / Multi-Agent Systems

Multi-Agent Systems

The future of multi-agent systems is not a collection of increasingly capable agents. It is an architecture of bounded authority, independent verification, traceable decisions, and accountable cooperation.

Connecting agents is now the easy part. MCP gives them tools, OpenAPI describes the systems behind those tools, and A2A lets one agent hand work to another. None of these standards decides who may act, on what evidence, under whose approval, or how to stop it. This page treats multi-agent systems as a problem of institutional design: how to separate roles, limit authority, verify independently, record decisions, and keep an organization able to say no. It ends with a reference flow you can adapt to your own company, and with the place of the Chinoba Decision Runtime in it.

01 / Why More Agents Are Not the Answer

Why More Agents Are Not the Answer

Enterprise AI has moved from chatbot, to agent, to specialized agents, to multi-agent systems. Each step added capability. The step that decides whether any of it can run safely inside a company is the one most roadmaps skip: governing how those agents relate to one another and to the people who answer for them.

One Workflow, Many Kinds of Knowledge

Customer Request ↓ Research ↓ Customer Data ↓ Pricing ↓ Contract Review ↓ Risk Evaluation ↓ Approval ↓ Execution

A quotation workflow is a small, ordinary example. Pricing rules, contract clauses, and risk policy each need their own context and their own checks.

Why One Agent Strains

Put every step inside a single agent and the failure is not that it cannot try. It is what trying does to the system:

  • context bloat — pricing rules, contract clauses, and risk policy compete for one context window
  • mixed knowledge — legal caution and sales optimism are reasoned out in the same undifferentiated pass
  • blurred responsibility — no step can be reviewed, retried, or held accountable on its own
  • poor reuse — the pricing logic cannot serve another workflow without dragging the rest along

Splitting the work solves the context problem and creates a different one. Once several agents research, propose, and act, the system has to answer questions no single agent ever faced: who goes first, who resolves a disagreement, what a partial failure does to everything downstream, and whose decision it finally was. The four familiar coordination patterns each answer part of that, and each opens a governance question of its own.

i

Handoff

One agent passes control and context to the next. Governance question: does the receiver inherit the sender's permissions, or only the task?

ii

Coordinator

A central agent assigns work and holds the overall state. Governance question: who checks the coordinator?

iii

Workflow

Agents are nodes in a predefined graph of steps and conditions. Governance question: who may change the graph?

iv

Actor Model

Independent actors exchange asynchronous messages. Governance question: where is the record of what was said and done?

02 / Connection Is Not Governance

Connection Is Not Governance: MCP, OpenAPI, and A2A

MCP, OpenAPI, and A2A are connection standards. They make it easier for agents to reach tools, systems, and one another. They do not decide whether a given agent should do a given thing, now, on this data. They do carry authentication and authorization mechanisms for who may connect, and those matter. But organizational policy, approval, verification, and audit are outside what the standards themselves set out to provide.

Standard Connects What it standardizes What it leaves open
MCP Agent ↔ tools and data How an agent discovers and calls tools, resources, and prompts. Whether this agent may use this tool, in this situation, on this data.
OpenAPI Software ↔ web API A machine-readable description of what an API accepts and returns. Which callers are entitled to which operations, and what a call means for the business.
A2A Agent ↔ agent Discovery, delegation, and progress updates between agents. Whether delegated work narrows, preserves, or quietly widens the delegator's authority.
Function / tool calling Model ↔ application function Structured arguments for a named function. Everything beyond the shape of the arguments.

Having a Tool Is Not Permission to Use It

An MCP server that can read a file is a different thing from one that can delete it. A search tool over internal documents is not a tool that updates a production database. A shell tool hands an agent a very wide reach into the outside world. All three speak the same protocol. The protocol can carry credentials, but which of them an agent should be allowed to call, and when, is a policy decision that lives outside it.

Delegation Is Indirect Permission

When agent A hands work to agent B over A2A, A is borrowing B's tools. If B holds broader permissions than A, delegation becomes a way to widen authority without anyone deciding to. The more that agents delegate to one another, the more the tool permissions behind each agent matter, and the less any one agent's own prompt can be relied on to hold the line.

Connection ≠ Authorization Having a tool ≠ permission to use it Delegation ≠ transfer of authority Agent consensus ≠ organizational decision

The agent frameworks sit in the same position. OpenAI Agents SDK, Claude Agent SDK, AutoGen, and LangGraph are routinely compared as rivals, but each is built around a different center of gravity — the agent, the context, collaboration, and explicit state. They are better read as components that cover different responsibilities, and enterprises increasingly combine them. Several offer useful building blocks, such as guardrails, approval pauses, and traces. What none of them can do for you is say who in your organization holds decision rights.

Framework Center of gravity Typical responsibility
OpenAI Agents SDK The agent Agent implementation, tool calling, and handoff between agents.
Claude Agent SDK Context and execution Code execution, file operations, and long-context management.
AutoGen Collaboration Distributed coordination and actor-style multi-agent work.
LangGraph State Graph-based state management and workflow orchestration.
03 / The Limits of the Central Orchestrator

The Limits of the All-Knowing Orchestrator

The tempting fix is one orchestrator that routes work, chooses tools, resolves conflicts, and signs off. It is easy to draw and easy to demo. It also gathers every risk the split was meant to remove into a single place.

Four Ways the Center Fails

  • single point of compromise — it holds every credential, so one injected instruction reaches everything
  • self-approval — the component that plans, routes, and judges is the same component, so nothing is independently checked
  • overload — it must understand every domain, and becomes the overloaded generalist you set out to replace
  • opaque accountability — decisions are made inside one context, and cannot be reconstructed from outside it

Coordination Without Sovereignty

An orchestrator is still useful, as long as it does coordination work: choosing which specialist receives a task, tracking where a request is, returning to a person when needed. What it should not hold is the authority to act. Authority belongs in separate, narrow components — gates, permits, verifiers, and records — that no agent, including the orchestrator, can rewrite.

Question Central orchestrator Specialists under institutional control
Where does authority live? Inside the orchestrator's prompt and credentials. In gates and permits outside any agent.
Who checks the work? The same system that produced it. A verifier with its own context and tools.
What does a compromise reach? Everything the orchestrator can touch. Only the scope of one role and one permit.
How is a decision reconstructed? From logs inside one context window. From an append-only evidence record kept outside the agents.
How does the system change safely? Edit the prompt and hope. Change a role, a policy, or a permit separately, with review.
04 / Eight Design Principles

Eight Design Principles for Governed Cooperation

These principles are about relationships between agents, and between agents and people. None of them depends on how capable any one agent happens to be.

i

Role separation

Each agent owns one kind of work and one kind of authority. The agent that proposes does not approve; the agent that writes does not ship.

ii

Least privilege

Credentials, tools, and data are scoped to the task and expire with it. A retrieval agent that can write has already failed its role.

iii

Escalation and approval

Responses are graded: act, propose, ask, stop, delegate. Risk — not habit — decides when a person enters.

iv

Evidence and Decision Trace

Record what was seen, which policy applied, and who approved. A structured record, not a chat transcript.

v

Independent verification

A Verifier or Challenge Agent works from its own context and tools, and cannot be configured by the author it checks.

vi

Kill switch and egress control

Permits can be revoked, agents frozen, and outside connections cut by a mechanism the agents do not control.

vii

Separated powers

Change, release, and connection authority are held by different parties, so no single approval unlocks all three.

viii

Auditability, reversibility, exceptions

Actions can be reviewed afterward and, where possible, undone. Exceptions go to a named owner instead of being improvised.

05 / A Reference Flow

A Reference Flow for Safe Enterprise Collaboration

Retrieve, propose, verify, approve, execute, audit. To make it concrete, take an operations team that wants agents to fix a recurring invoice error: find the cause, patch the script that generates the invoices, and re-issue the affected ones.

Stage Who What happens What it must not do
1 · Retrieve Research / Retrieval Agent Reads invoice records, error logs, and the billing policy through read-only connections, and returns a cited evidence pack. Write anywhere, or follow instructions found inside the documents it retrieves. Retrieved text is data.
2 · Propose Planning Agent and Implementation Agent The planner states the root cause, the patch, and the list of affected invoices. The implementer drafts the patch on a sandbox branch and opens a change request. Call production tools, merge its own change, or widen the plan after review.
3 · Verify Verifier / Challenge Agent Re-runs the tests, checks that each claim in the plan is backed by the evidence, and records its objections. It works from its own context with its own read-only access. Edit the patch or plan, or be briefed on what the author expects to hear.
4 · Approve Policy / Authorization Gate, then Human Approver The gate checks policy and amount limits, confirms that author, verifier, and approver differ, and issues a permit naming target, operation, expiry, and number of uses. A person approves anything customer-facing or above threshold. Issue a permit it cannot explain, or approve a bundle of future actions in one step.
5 · Execute Execution Runner (deterministic, permit-bound) Deploys the approved build and re-issues the listed invoices, one permitted operation at a time. Act outside the permit, or retry beyond its allowed count.
6 · Audit Audit Log / Evidence Store and monitor Records the evidence, verdict, policy version, approval, permit, and result, plus how to reverse it. A monitor with read-only access flags drift and anomalies. Be writable by the agents whose work it records.

Not Every Step Needs a Person

Requiring approval for everything fails in two directions. Reviewers drown in routine requests and stop reading them, and the agent becomes a slow proxy for human clicks. Approval-free autonomy fails the other way: mistakes and overreach surface only after the damage. A more workable model lets agents act freely inside narrow, pre-agreed bounds, records everything, and brings in a person according to risk.

Act → compare, summarize, look up Propose → draft a plan or recommendation Ask → high-impact or ambiguous update Stop → policy or contract conflict Delegate → needs specialist expertise

Human-in-Authority, Not Just in the Loop

A person who clicks "approve" on a screen is not automatically an authority. In this flow the Human Approver is there because the organization placed decision rights with that role, and the gate shows them the same evidence, policy result, and verifier objections it used. Their job shifts from checking each action to designing the bounds, deciding exceptions, and answering for the outcome.

Exceptions need a path too, or people will invent one. If the verifier keeps objecting, the work goes to a named owner rather than back into a loop. If something urgent cannot wait, a break-glass route lets a designated approver grant a narrow, time-boxed permit, which is logged as an exception and reviewed afterward. If a permit turns out to be wrong, it can be revoked before it is used, and the trace records what the reversal would involve.

06 / Separating Change, Release, and Connection

Separating Change, Release, and Connection

Two failure patterns deserve to be named plainly: an AI that builds its own connection to the outside world, and a code-changing agent that can deploy what it writes. Both come from folding several separate powers into a single identity.

When an Agent Can Create Its Own Connection

A new tool endpoint, plugin, or MCP server can quietly add shell access, expose stored credentials, or open an outbound path. If agents can register such things themselves, the boundary you drew exists only until the first convenient shortcut. The design response is to treat a connection as an asset with an owner:

  • agents may request a connection as a ticket; they never register one
  • every connection has an owner, a purpose, a scope, and a risk level
  • outbound traffic is denied by default and allowed through a proxy against that list
  • a new connection starts read-only and is scanned and tested before it widens

When the Agent That Writes Code Can Ship It

Code generation and deployment are different powers, and one credential should never span both. The agent works on a sandbox branch with no production access. A separate gate issues a release permit tied to a specific signed build, so any change after approval invalidates the permit. The pipeline, not the agent, performs the deploy.

The general rule: proposals may stay fluid, but whatever touches the world must be fixed, signed, and verifiable before it runs.

Risk Typical cause Design response
Agent creates its own connection Registration is open to agents; egress is allowed by default. Connection registry with human owners, allow-listed egress, read-only start.
Code-changing agent deploys itself One credential spans the repository and production. Separate keys; release permit pinned to a signed artifact.
Verifier simply agrees with the author Shared context, prompts, and incentives. Independent context and tools; objections must be answered, not overridden by the author.
Delegation widens authority A handoff inherits the delegator's tools, or the delegate's. Delegation narrows by default; permits are scoped per hop.
Instructions hidden in retrieved content Retrieved text is treated as a command. Retrieval agents are read-only; the gate decides, not the model.
Runaway loops and cost No step, spend, or permit-count limit. Hard budgets per run, permit counts, and a kill switch.

A kill switch is only as good as its independence. It should be held by an identity the agents cannot use, and it should do four things at once: revoke outstanding permits, suspend agent credentials, close outbound connections, and freeze queued work. Rehearse it. A switch nobody has tested is a diagram. Where an action cannot be undone, require a stronger gate before it runs rather than a better apology afterward.

07 / Evidence and Decision Trace

Evidence and Decision Trace at the Center

The record is what makes every other principle checkable. Independent verification needs something to verify, audit needs something to read, and a kill switch needs a signal to act on.

More Than a Log

An application log says that something happened. A Decision Trace preserves why it was allowed to happen.

  • evidence — what the agents saw, with sources
  • reasoning — why this plan, and which objections were raised
  • authority — which policy version and which approver, on what basis
  • outcome — what was executed, what was observed, and how to reverse it

Written by Infrastructure, Not by Agents

An agent's own account of what it did is a claim, not evidence. The record has to be captured by the gate, the runner, and the platform around the agents, from what the agents submitted and did, so that an agent that misbehaves cannot also edit the story. That is what lets a person, months later, replay a decision and see what was known at the time.

08 / Institutions, Not Personalities

Institutional Analogies — and Where They Stop

Human institutions have worked on this problem for centuries: separating duties, limiting delegation, keeping records, revoking access, aligning incentives. The analogy is useful when it is applied to structure. It misleads when it is applied to psychology.

Human institution Agent-system counterpart Where the analogy stops
Separation of duties — the person who writes the check does not sign it Author, verifier, approver, and runner are different parties Agents can share a model, a prompt lineage, and blind spots. Independence has to be engineered through separate context, tools, and often a different model, not assumed.
Delegation with limits — power of attorney, spending authority A permit with target, operation, expiry, and use count A person reads the spirit of a mandate. An agent follows its letter, so scope has to be stated literally.
Records and audit — ledgers, minutes Decision Trace written by infrastructure An agent's self-report is not a record. The recorder must be someone other than the actor.
Revocation — suspending access, recalling authority Kill switch, permit revocation, egress cut-off It has to work at machine speed and without the agent's cooperation.
Incentives — reputation, liability, consequences Trust earned from traced history; a named owner for every agent An agent has no stake in the outcome. Accountability attaches to the people who own the agent and its policy.

This is why the page talks about roles and not personalities. A role here is a permission profile with a defined interface: what the agent may read, propose, or do, and nothing more. Describing an agent as honest, careful, or trustworthy hides engineering choices behind character traits. What can be said, and checked, is which evidence it was given, which bounds applied, and what the record shows. The accountable party is always a person or team — which is why every agent should have a named owner.

09 / Taking This to Your Organization

Taking This to Your Own Organization

You do not need a full runtime to begin. You need to answer a few questions before agents get more reach than anyone has reviewed. Start with one workflow, and work through these in order.

01

Inventory what already exists

Find the agents, MCP servers, plugins, and stored credentials already in use, including the ones individuals installed for convenience. Record an owner, purpose, and scope for each. Inventory tools can help, but a spreadsheet beats nothing.

02

Classify actions by consequence

Sort actions into reading, drafting, reversible writes, irreversible or external actions, and anything involving money, law, or safety. Decide act, propose, ask, or stop for each class.

03

Split the keys

Before adding more agents, move change, release, and connection credentials to different identities. This is often the cheapest and most effective step.

04

Put a gate between proposal and execution

It can start simple: a permit service or approval workflow that agents cannot bypass, that issues scoped and expiring grants, and that fails closed.

05

Add an independent verifier where it matters most

Begin with the highest-consequence class of action. Give the verifier its own context and read-only access, and make its objections binding until answered.

06

Write the trace and rehearse the stop

Keep the record outside the agents. Then test it: replay a past decision from the record, and trigger the kill switch on a schedule.

Five Questions for Any Agent Deployment

Who can this agent act as? What can it change without asking? Who checks its work, and how independently? How do we stop it, and how fast? Can we reconstruct last Tuesday's decision?

Reading the Answers

If the first answer is "the service account for everything," authority has not been separated. If the third is "the same agent, asked again," nothing is independent. If the fifth is "from the chat history," accountability depends on luck. These are organizational findings, not model-quality findings, and they are cheaper to fix before the agents are capable enough to make the gaps expensive.

10 / Chinoba Decision Runtime and Beyond

Where Chinoba Decision Runtime Fits, and Beyond

Chinoba's Decision Runtime (CDR) is one concrete way to build the layer this page describes: a runtime between what agents produce and what organizations let happen. Its core distinction is the one running through every section above.

Intelligence and Authority

AI Agent → Signals and Candidates Decision Runtime → Decisions Command Permit → Execution

Agents produce Signals and Candidates. The runtime evaluates them against policy, boundary, risk, and human authority, and only a Command Permit authorizes execution. Everything is recorded as Decision Trace.

Five Distinctions

AI Agent ≠ Decision Authority Agent Framework ≠ Enterprise Governance Agent Consensus ≠ Organizational Decision Decision ≠ Execution Permission Distributed Agents ≠ Distributed Authority
01

Centralized Runtime

Agents → Central Runtime → Decision → Execution. Policy, identity, and audit sit in one place. Best where connectivity is stable and unified control comes first.

02

Cooperative Edge Runtime

CDR Edge decides locally at a store, factory, or branch while the central runtime keeps policy, identity, and audit consistent. Useful where latency, resilience, or physical systems matter.

03

Federated Runtime

Each runtime keeps its own decision authority and data sovereignty, cooperating through delegation contracts and a shared, verifiable trace. Suited to cross-organization work.

Distributing agents is not the same as distributing authority. A company can run agents at a hundred sites and keep decision rights central, or run one agent and spread authority across partners. Across organizations the questions sharpen: an explicit delegation contract, a federated identity, a basis for trusting another party's decision, and a shared trace. Trust there is not a credential issued once. It accrues from a counterpart's record of staying within declared authority, which is the subject of the Trust Infrastructure research. Carried to its limit, the same design becomes a question about how people, agents, organizations, and physical systems coordinate while each keeps its own authority and responsibility — the Runtime Society line of inquiry. The coordination side of this story is developed in AI Coordination Engineering.
